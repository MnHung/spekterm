# ui-localization Specification

## Purpose

app 中所有**使用者可見的文案**以**當前的 UI 語言**呈現，且皆自該語言的**單一字典**取得 ——
主行程與 renderer 共用同一份，key 具編譯期的型別安全，字典之間的完整對應由一道機械守衛保證，
並由另一道守衛擋住「產品原始碼中含 CJK 的字串字面值」。

後面那道守衛是必要的，而非加分項：文案之所以會被寫死在程式碼裡，不是因為有人決定這麼做，
而是因為沒有東西擋著 —— 而它與「app 支援幾種語言」無關。

本能力涵蓋三個容易被忽略的邊角：

- **`aria-label` 同時是選擇器**。文案與選擇器分離為兩份字面值時，失去同步的徵狀是「選不到
  元素」而非「斷言失敗」—— 而多語讓這件事更尖銳：**標籤自己也會被翻譯**，於是驗收在哪一種
  語言下執行，選擇器就得用哪一種語言的字典。
- **一切 locale 衍生的呈現**（相對時間、時刻、數字、使用者看得到的排序）取自同一處，
  而僅為確定性而存在的內部定序**不在**其中，且逐一具名豁免。
- **寫給 agent 執行的指令不屬於使用者可見的文案，即使它出現在畫面上** —— 被填入 agent 輸入處
  而尚未送出的那一則 prompt 落在「寫進 pty 供人閱讀」的字面定義之內，而它恆為英文。

## Requirements

### Requirement: 使用者可見的文案為當前 UI 語言

app 中每一個**使用者可見的文案** SHALL 以**當前的 UI 語言**呈現。

「使用者可見的文案」SHALL 包含以下六類 —— 它們的載體不同，但都會抵達使用者的眼睛：

1. **renderer 的介面文字**：JSX 的文字節點、`aria-label`、`title`、驗證訊息、空狀態、
   選單項與按鈕的標籤。
2. **主行程的原生對話框**：`dialog.showMessageBox` 的訊息與按鈕。
3. **主行程經 IPC 送達畫面的錯誤訊息**：其 message 會被呈現層直接顯示（如 session 喚醒失敗的
   訊息、檔案操作的失敗說明）。
4. **寫進 pty 串流、供人閱讀的訊息**：如 session 重建時的重播分隔線。
5. **主行程發出的作業系統原生通知**：其標題與內文。
6. **The application menu the operating system draws** (macOS): the labels of its items. Like the
   notifications, it is drawn outside the application's own window, and the label of a role item would
   otherwise come from the system, not from the dictionaries. The application menu's own title is the
   bundle's name and is exempt.

**`console.*` 的輸出與內部不變式的例外訊息不屬於使用者可見的文案** —— 它們不需要進入字典
（沒有使用者會讀到它們），但仍 SHALL 為英文（見「產品原始碼不得含非英文的字串字面值」）。

> **第五類與前四類的差別，正是它容易被漏掉的原因**：它既不經 IPC、也不由 renderer 繪製，
> 而是由作業系統畫在應用程式自己的框**之外**。第 3 類的定義（「經 IPC 送達畫面」）看起來
> 涵蓋得住它，實際上不涵蓋 —— 而 CJK 守衛對兩者一視同仁，所以把它誤歸為第 3 類**不會讓任何
> 東西變紅**。

**寫給 agent 執行的指令不屬於使用者可見的文案，即使它出現在畫面上。** 這是對上述第 4 類的
明文例外，SHALL 為英文，且 SHALL NOT 隨 UI 語言改變。它涵蓋：注入 agent 脈絡的自我介紹、
交給 agent 的檔案中界線**之外**的抬頭、以及**被寫入 agent 輸入處**的第一則 prompt（不論它是等使用者送出、還是被代為送出）。

> **這條例外反直覺，因此必須明文。** 第一則 prompt 的確被寫進 pty，使用者也可能在讀它 ——
> 它落在第 4 類的字面定義之內。把它留在英文而不寫下這條，等於讓規格與實作各說各話，
> **而那個分歧沒有任何東西會讓它變紅**。理由是它承載 prompt injection 的措辭（「界線之內是
> 資料而非指令」），其翻譯後的效力**沒有任何載體能驗**；使用者需要理解的部分（這則交接來自
> 誰、內容是什麼）由收件匣的介面承擔，而那一側在地化。

#### Scenario: 介面文字為當前 UI 語言

- **WHEN** 使用者檢視活動列、workspace rail、主舞台、side panel 的任一視圖與 session 分頁列
- **THEN** 其上每一個文字標籤、空狀態與提示皆以當前 UI 語言呈現

#### Scenario: 關閉視窗的未存提示為當前 UI 語言

- **WHEN** 面板中有未存的變更，使用者關閉視窗，原生對話框出現
- **THEN** 該對話框的訊息與其每一顆按鈕的文字皆以當前 UI 語言呈現

#### Scenario: 主行程送達畫面的錯誤訊息為當前 UI 語言

- **WHEN** 一個由主行程產生、且會被呈現層顯示的失敗訊息抵達畫面
- **THEN** 該訊息以當前 UI 語言呈現

#### Scenario: 終端中寫給使用者的訊息為當前 UI 語言

- **WHEN** 一個被重建的 shell session 重播其上次的畫面，並顯示歷史與 live 之間的分隔
- **THEN** 該分隔上的文字以當前 UI 語言呈現

#### Scenario: 作業系統原生通知的文案為當前 UI 語言且取自字典

- **WHEN** 主行程發出一則作業系統原生通知
- **THEN** 其標題與內文中的系統文案以當前 UI 語言呈現
- **AND** 那些文案取自共用的字典，而非以字面值寫在主行程模組中

#### Scenario: 預填的 prompt 不隨 UI 語言改變

- **WHEN** UI 語言為非英文，使用者接受一則待處理項目，agent session 開啟並填入第一則 prompt
- **THEN** 該 prompt 為英文
- **AND** 同一畫面上屬於介面的文字（分頁標籤、狀態列、收件匣）以當前 UI 語言呈現

#### Scenario: 注入 agent 脈絡的文字不隨 UI 語言改變

- **WHEN** UI 語言為非英文，一個 agent session 啟動
- **THEN** 經 `SessionStart` 注入其脈絡的自我介紹為英文

#### Scenario: The macOS application menu is in the current UI language

- **WHEN** on macOS the UI language is not English and the application menu is opened
- **THEN** each of its items is labelled in that language, from the shared dictionaries

### Requirement: 使用者可見的文案由 i18n 層供應，不得硬編於程式碼

使用者可見的文案 SHALL 自一份**字典**取得，SHALL NOT 以字面值寫在元件、主行程模組或任何
產品程式碼中。

該字典 SHALL 為**單一份事實**，且 SHALL 同時供應主行程與 renderer —— 兩者是不同的執行環境，
但它們的文案屬於同一個產品。

字典的 key SHALL 具有**編譯期的型別安全**：引用一個不存在的 key SHALL 使型別檢查失敗，
SHALL NOT 延遲到執行期才以「把 key 印在畫面上」的方式暴露。

#### Scenario: 主行程與 renderer 取用同一份字典

- **WHEN** 檢視主行程與 renderer 各自取得文案的來源
- **THEN** 兩者解析到同一份字典檔

#### Scenario: 引用不存在的 key 於編譯期失敗

- **WHEN** 產品程式碼引用一個字典中不存在的 key
- **THEN** `npm run typecheck` 以非零碼結束

#### Scenario: 元件不含文案的字面值

- **WHEN** 檢視任一呈現使用者文案的元件
- **THEN** 該文案來自字典的 key，而非寫在元件中的字串字面值

### Requirement: 產品原始碼不得含非英文的字串字面值

`src/` 之下的產品原始碼中，**字串字面值、模板字面值與 JSX 的文字節點** SHALL NOT 含有 CJK 字元。
此規則 SHALL 由一道自動化守衛強制，並 SHALL 隨 `npm test` 執行。

**註解 SHALL 豁免** —— 本 repo 的既有慣例是「程式碼英文、註解與文件繁體中文」，本能力不改變它。
豁免註解正是這道守衛的核心語意，因此其實作 SHALL 依據語法樹（區分字串與註解），
SHALL NOT 以逐行的字面比對判定。

測試檔（`*.test.ts`）與 `scripts/` 之下的開發工具 SHALL 豁免。

**這道守衛是必要的，而非加分項**：文案之所以會變成中文，不是因為有人決定用中文，而是因為
沒有東西擋著。少了守衛，本能力交付的狀態會被後續的 change 逐次磨掉。

#### Scenario: 含 CJK 的字串字面值使守衛失敗

- **WHEN** 產品原始碼中有一處字串字面值含 CJK 字元
- **THEN** 守衛以非零碼結束，並指出該處的檔案與位置

#### Scenario: 繁體中文的註解不使守衛失敗

- **WHEN** 產品原始碼含有繁體中文的行註解、區塊註解或 JSX 註解，且無任何含 CJK 的字串字面值
- **THEN** 守衛通過

#### Scenario: 守衛以對照組證明其偵測有效

- **WHEN** 將一份刻意含 CJK 字串字面值的來源交給守衛的偵測邏輯
- **THEN** 該處被回報 —— 一道從未證明自己抓得到東西的守衛，與沒有守衛無法區分

### Requirement: 以文案定位介面元素的程式碼自字典取得該文案

產品程式碼或驗收腳本若以**文案**（如 `aria-label`）定位一個介面元素，該文案 SHALL 自字典取得，
SHALL NOT 以字面值硬編。

理由是這個 repo 的一個結構性事實：**`aria-label` 同時是選擇器**。驗收不得為此在產品 UI 上掛
`data-*`（既有紀律），於是 probe 只能以 `role` 與 `aria-label` 定位元素；而 `Ctrl+T` 的實作是
「找到既有的建立入口並觸發它」，靠的正是 `aria-label`。

**文案與選擇器一旦分離為兩份字面值，它們就會在某一次改文案時失去同步 —— 而失去同步的徵狀是
「選不到元素」，不是「斷言失敗」。** `Ctrl+T` 更是連紅燈都不會有：它是字串比對，改了文案不會
編譯錯，快捷鍵直接靜默失效。

#### Scenario: 鍵盤開啟建立入口不依賴硬編的文案

- **WHEN** 檢視 `Ctrl+T` 定位建立 session 入口所使用的文案
- **THEN** 該文案取自字典

#### Scenario: 驗收腳本的選擇器不依賴硬編的文案

- **WHEN** 檢視驗收腳本中以 `aria-label` 構成的選擇器
- **THEN** 其文案取自字典，而非腳本中的字面值

### Requirement: locale 衍生的呈現與 UI 語言一致

renderer 文件的 `lang` SHALL 宣告為當前的 UI 語言，並 SHALL 於語言改變時隨之更新。

**一切 locale 衍生的呈現** SHALL 以當前的 UI 語言格式化，其 locale SHALL 取自 i18n 層當前的
語言，SHALL NOT 硬編、亦 SHALL NOT 沿用執行環境的預設 locale。作用域 SHALL 包含：相對時間、
時刻與日期、數字、以及**使用者看得到的字串排列順序**。

**與語言無關的內部定序不在作用域內，且 SHALL 被逐一具名地豁免**：僅為使呼叫端看到穩定順序
而做的收斂、演算法在分數相同時的 tie-break、以及對非人讀識別碼的比較，其順序 SHALL NOT 隨
UI 語言改變。

> **這條區分是必要的，而不是為既有程式碼開的後門。** 把兩者一視同仁會改壞既有行為：一個
> 隨語言變動的 tie-break 會讓「同分時的排名」成為環境的函數，而釘住它的測試就變成在測環境。
> 反過來，把區分寫成「守衛的豁免清單」而非規格條款也不行 —— 那樣它就只是一份沒有理由的
> 名單，下一個人分不出哪些豁免是有論證的、哪些是當初懶得改的。**每一條豁免 SHALL 帶理由。**

**這些呈現 SHALL 自單一處取得其 locale，SHALL NOT 由各呼叫點各自決定**，且該收斂 SHALL 由一道
隨 `npm test` 執行的原始碼守衛維持，該守衛 SHALL 經對照組驗證。

> **這道守衛不是加分項，它有證據。** 本能力成立時 app 只有一種語言，而在那個前提下長出了三處
> 各自不同的做法：一處硬編了另一個 locale 的排序規則、一處硬編了英文的數字格式、一處沿用執行
> 環境的預設 —— 於是一個宣稱全英文的介面，在一台非英文的機器上把時刻顯示成了當地格式。
> **三處都沒有任何東西會變紅。** 紀律在沒有守衛時已經失效過了。

#### Scenario: 相對時間以當前 UI 語言呈現

- **WHEN** 檔案樹呈現一個最後修改於數小時前的項目
- **THEN** 該列的相對時間以當前 UI 語言呈現

#### Scenario: 時刻不沿用執行環境的預設 locale

- **WHEN** 執行環境的預設 locale 與 UI 語言不同，狀態列呈現一個時刻
- **THEN** 該時刻以 UI 語言的 locale 格式化，而非以執行環境的預設 locale

#### Scenario: 文件宣告的語言與 UI 一致

- **WHEN** 檢視 renderer 文件根元素的 `lang`
- **THEN** 其值為當前的 UI 語言

#### Scenario: 語言改變後文件的宣告隨之更新

- **WHEN** 使用者改變 UI 語言
- **THEN** 文件根元素的 `lang` 成為新的語言

#### Scenario: 內部定序不隨 UI 語言改變

- **WHEN** UI 語言改變，而某個順序僅為內部的確定性而存在（如同分時的 tie-break）
- **THEN** 該順序不變

#### Scenario: 於收斂處之外取得 locale 即失敗

- **WHEN** 產品原始碼於該單一收斂處之外自行決定一個格式化或排序的 locale
- **THEN** 守衛以非零碼結束，並指出該處

### Requirement: UI 語言可由使用者選擇並持久化

app SHALL 提供一組**受支援語言**的清單，使用者 SHALL 能於設定介面中選擇其一。所選的語言
SHALL 立即生效，SHALL NOT 要求重新啟動，且 SHALL 跨重啟保留。

受支援語言的清單 SHALL 為**單一來源**：可選項、落盤值的接受範圍、以及字典完整性的定義域
SHALL 皆自它推導。

語言選項的標籤 SHALL 為各該語言的**自稱**（如 `English`、`繁體中文`），且 SHALL NOT 隨當前
UI 語言改變 —— **一個看不懂當前語言的使用者，必須能在清單中認出自己的語言**。

落盤的語言值 SHALL 以**白名單查表**接受：不在受支援清單中的值 SHALL 視為未設定，
SHALL NOT 被當作一個合法的選擇。「檔案壞了」與「使用者選了某個語言」SHALL NOT 成為同一件事。

#### Scenario: 選擇語言後介面立即改變

- **WHEN** 使用者於設定介面選擇另一種受支援的語言
- **THEN** 介面文字立即以該語言呈現，且未要求重新啟動

#### Scenario: 語言選擇跨重啟保留

- **WHEN** 使用者選擇一種語言後結束並重新啟動 app
- **THEN** 介面以該語言呈現

#### Scenario: 語言選項以各自語言的自稱呈現

- **WHEN** 使用者於任一 UI 語言下開啟語言選擇
- **THEN** 每個選項的標籤為該選項所指語言的自稱，且不隨當前 UI 語言改變

#### Scenario: 落盤中不受支援的語言值視為未設定

- **WHEN** 持久化的偏好中語言欄位為一個不在受支援清單中的值
- **THEN** app 以未設定的方式處理它，而非以該值啟動

### Requirement: 首次啟動的語言取自作業系統的偏好語言

**當且僅當持久化的偏好尚不存在時**，app SHALL 以作業系統回報的**偏好語言順序**決定初始語言：
取該順序中第一個受支援的語言，皆不受支援時 SHALL 退回英文。

**判準為「偏好尚不存在」，SHALL NOT 為「語言欄位未設定」。** 兩者的差別在升級路徑上：
既有使用者的偏好已經存在（其中有他既有的設定），以欄位未設定為判準會讓**他的 app 在升級後
自行改變語言** —— 那是一次沒有人要求過的行為改變。

**「偏好尚不存在」SHALL 嚴格等同於「從未啟動過」。** 任何會讓偏好檔消失而 app 仍繼續執行的
路徑（如內容不可信時的隔離）SHALL 於其後使偏好重新存在 —— 否則「檔案壞過一次」的使用者會在
下一次啟動時莫名其妙換了語言，而上述整個判準就只擋得住升級、擋不住這條路。

該映射 SHALL 為一個可獨立驗證的純粹轉換（輸入為語言標籤的有序清單，輸出為受支援語言之一），
且 SHALL NOT 以「是否為打包後的執行」為閘 —— 那會使這條路徑在開發與驗收下完全不被執行。

#### Scenario: 首次啟動採用作業系統的偏好語言

- **WHEN** 持久化的偏好不存在，且作業系統回報的偏好語言順序中第一個受支援的語言為某語言 L
- **THEN** app 以 L 啟動

#### Scenario: 作業系統的偏好語言皆不受支援時退回英文

- **WHEN** 持久化的偏好不存在，且作業系統回報的偏好語言皆不在受支援清單中
- **THEN** app 以英文啟動

#### Scenario: 偏好被隔離後不觸發偵測

- **WHEN** 持久化的偏好因內容不可信而被隔離，app 以預設繼續，其後再次啟動
- **THEN** 不進行偵測，語言維持英文
- **AND** 「持久化的偏好不存在」因此嚴格等同於「從未啟動過」

#### Scenario: 既有偏好不因升級而改變語言

- **WHEN** 持久化的偏好已存在但其中沒有語言欄位，app 啟動
- **THEN** app 以英文啟動，SHALL NOT 依作業系統的偏好語言改變

### Requirement: 語言的改變同時抵達主行程與 renderer

UI 語言改變時，**主行程與 renderer 兩者的文案來源** SHALL 皆改變。兩者是不同的執行環境、
各自持有一份 i18n 狀態，而它們的文案屬於同一個產品。

套用的順序 SHALL 為**主行程先、renderer 後** —— 反過來時，套用失敗的那一刻畫面已是新語言而
原生對話框與通知仍是舊語言，**而那個分岔不會產生任何錯誤**。

#### Scenario: 語言改變後主行程的文案隨之改變

- **WHEN** 使用者改變 UI 語言，隨後觸發一個由主行程產生並送達畫面的失敗訊息
- **THEN** 該訊息以新的語言呈現

#### Scenario: 主行程拒絕該語言時畫面不搶先改變

- **WHEN** 語言的套用在主行程失敗
- **THEN** renderer 的文案維持原語言

### Requirement: 每一種語言的字典完整性由機械守衛保證

每一種受支援語言的字典 SHALL 與基準語言的字典完整對應，且該對應 SHALL 由一道隨 `npm test`
執行的守衛檢查。守衛 SHALL 檢查以下各項，缺一不可：

1. **基底 key 相等** —— 去除複數後綴之後，兩者的 key 集合相同。
2. **複數類別符合該語言的 CLDR 規則** —— 每個基底 key 在語言 L 的字典中所具備的複數後綴集合，
   恰為 L 的複數類別集合。**SHALL NOT 以「key 集合完全相同」判定** —— 語言之間的複數類別數目
   本就不同，那樣的守衛對任何正確的翻譯都會失敗。
3. **插值變數集合相等** —— 同一個 key 在各語言中所引用的變數集合相同。
4. 值不得為空字串。

**第 3 項是四項中失效最不顯眼的一項**：翻譯漏掉一個變數時，畫面上是一句**少了那個值的話**
（少了檔名、少了 repo 名），沒有錯誤、沒有紅字、也沒有型別問題。

守衛 SHALL 經對照組驗證，且對照組 SHALL 涵蓋上述四項各自的違反方式。

#### Scenario: 缺少 key 的字典使守衛失敗

- **WHEN** 某受支援語言的字典缺少一個基準語言中存在的基底 key
- **THEN** 守衛以非零碼結束，並指出該 key

#### Scenario: 符合 CLDR 的複數類別不使守衛失敗

- **WHEN** 某語言的複數類別少於基準語言，其字典據此僅提供該語言所需的複數後綴
- **THEN** 守衛通過

#### Scenario: 漏掉插值變數的翻譯使守衛失敗

- **WHEN** 某個 key 的翻譯未引用基準語言中該 key 所引用的一個變數
- **THEN** 守衛以非零碼結束，並指出該 key 與該變數

#### Scenario: 守衛以對照組證明其偵測有效

- **WHEN** 將四種違反（缺 key、複數後綴不符、漏變數、空值）各自交給守衛的偵測邏輯
- **THEN** 每一種皆被回報

### Requirement: 已持久化的文字，其語言於寫入當下固定

由 app 產生、且**與內容一同持久化**的文字（如攝入時寫入待處理項目本文的抬頭與截斷說明），
其語言 SHALL 於**寫入當下**決定並固定。呈現該內容時 SHALL NOT 重新翻譯它。

**理由是一條既有的不變式**：這類文字所在的欄位，其「呈現給使用者的那一份」與「交給 agent 的
那一份」被要求**逐字元相同**（見 `agent-intake`）。呈現層若在顯示時重新翻譯，畫面上的那一份
就與磁碟上的那一份分岔了。

**這個分岔只在使用者改變過語言之後才會出現** —— 一輪未曾改變語言的驗收碰不到它，因此它的
載體 SHALL 自行造出「改變語言」這個動作。

#### Scenario: 改變語言後既有項目的本文不變

- **WHEN** 一則待處理項目於語言 A 之下被攝入，使用者隨後將 UI 語言改為 B，並檢視該項目
- **THEN** 其本文仍以語言 A 呈現

#### Scenario: 改變語言後呈現與交付仍逐字元相同

- **WHEN** 承上，使用者接受該項目
- **THEN** 交給 agent 的檔案中界線之內的內容，與畫面上呈現的本文逐字元相同

### Requirement: 驗收腳本明確指定被測 app 的語言

驗收腳本 SHALL **明確指定**被測 app 執行時的 UI 語言，SHALL NOT 讓它取決於執行機器的
作業系統設定。該指定 SHALL 由一道隨 `npm test` 執行的原始碼守衛維持。

**失效方向決定了這條為何必要**：驗收腳本以文案定位介面元素（見「以文案定位介面元素的程式碼
自字典取得該文案」），而那些文案取自基準語言的字典。被測 app 若以另一種語言啟動，腳本的
**症狀是「選不到元素」** —— 它看起來像產品壞了，不像驗收設定錯了。

例外 SHALL 逐一具名並帶理由，且 SHALL 屬於以下兩類之一：

1. **不指定語言，且其斷言 SHALL NOT 依賴任何取自字典的文案** —— 例如只驗證應用程式身分、
   路徑或原生模組載入的段落。
2. **以驗證語言的決定機制本身為目的的段落** —— 它必須讓語言取決於被驅動的來源（那正是它在
   驗的東西），因此 SHALL 明確指定它所驅動的**那個來源**，且 SHALL NOT 依賴執行機器既有的設定。

**第 2 類不是第 1 類的破口**：第 1 類說的是「不依賴字典」，而第 2 類的斷言必然依賴字典
（它就是在驗「介面變成那個語言了嗎」）。把兩者混為一談的條款會讓偵測那條路**無法被驗收**。

#### Scenario: 每個啟動被測 app 的位置都指定語言

- **WHEN** 檢視驗收腳本中每一處啟動被測 app 的位置
- **THEN** 其被測 app 的 UI 語言為明確指定，或該位置屬於具名的例外

#### Scenario: 驗證偵測機制的段落指定其所驅動的來源

- **WHEN** 檢視驗證「首次啟動的語言取自作業系統」的那一段
- **THEN** 它明確指定了作業系統回報偏好語言所依據的來源，而非沿用執行機器既有的設定

#### Scenario: 移除任一處的指定即失敗

- **WHEN** 任一處啟動位置的語言指定被移除
- **THEN** 守衛以非零碼結束
