# Slack 來源與機密（`slack-*` / `secret-store`）的教訓

> 這一份的定位與 `CLAUDE.md` 相同 —— 「不知道就會踩、而且失敗是靜默的」。觸發條件夠明確
> （動到 `src/main/slack-*`、`src/main/secret-store.ts`、`scripts/probe-slack.mjs`、
> `scripts/lib/stub-slack.mjs`、或任何會把憑證交給第三方的東西），所以搬出來讓它不必每個
> session 都佔位。**它不是補充讀物，是那些模組的前提。**

## 一、去重的權威必須是**收件匣自己的紀錄**，不是本能力的水位

第一版的設計是「把會進去重摘要的第三方字串與水位一起快照，重新推導時沿用」。那個設計有一個洞：
**它保護不了促使它存在的情境。** 會觸發重新推導的主要原因**正是水位遺失**（重裝、設定還原、
設定檔損毀隔離）—— 而快照若與水位同居一檔，那時它一起遺失。

處置是問收件匣（`intake-store.get(adapter, id)`）。這使假警告**在結構上不可達**，而不只是變罕見：

1. 收件匣**有**該識別碼 ⇒ 不交付 ⇒ 不做內容比對；
2. 收件匣**沒有** ⇒ `deliver()` 走「全新」那一支 ⇒ **同樣不做內容比對**。

兩條路都不經過那個會跳警示的分支。**於是任何額外的快照狀態都不需要了。**

> 這條倚賴一個實測的性質：`intake-store.ts` 的 `setState()` **只改狀態，沒有任何路徑刪除紀錄**
> —— 接受過、忽略過的項目永遠留著。**那個性質是承重的**：日後若為 `intake.json` 加上清理或
> 保留期，這條論證即刻失效，而失效的症狀是「偶爾冒出一則看不懂的搶佔警示」。

## 二、去重摘要涵蓋**六個**欄位，其中兩個第三方隨時可改

`digestOf`（`intake-store.ts`）比對的是 `originKind` / `originId` / `title` / `body` / `actor` /
`originLabel`。**只讓本文穩定是不夠的**：

| 欄位／來源 | 什麼時候會變 |
|---|---|
| `originLabel` | 頻道改名 —— **一次改名影響該頻道所有被重新推導的提及** |
| `actor` | 發話者改自己的 display name |
| 本文中的提及呈現 | `<@U123>` 必須解析成 `@顯示名稱`（否則使用者讀到一串 id），於是顯示名稱被烤進本文 |
| 本文中的 link unfurl | unfurl 是訊息貼出**之後**非同步補上的 —— 隔 1 秒取與隔 1 天取不同 |

`intake-schema.ts` 的註解就寫著 `originLabel`「是可變的字串」。**動去重相關的任何東西之前
先回來看這張表。**

## 三之前：**列舉頻道與讀取歷史是兩組不同的 scope**（dogfood 踩到）

`conversations.history` 只要 `channels:history` 那一組，但 **`users.conversations`（列出使用者
在哪些頻道）要 `channels:read` / `groups:read` / `mpim:read` / `im:read`**。少了後者，
`users.conversations` 回 `missing_scope`，頻道清單是空的，於是**整條回補一則都掃不到** ——
而症狀只是「收件匣是空的」。

完整的 user token scope 清單：

```
channels:history  groups:history  im:history  mpim:history   # 讀得到訊息
channels:read     groups:read     im:read     mpim:read      # 列得出頻道
users:read                                                    # 把 <@U123> 換成人名
```

**改完 scope 一定要 Reinstall**，而且要重新複製 token。

## 三、Slack 對業務錯誤回 **HTTP 200**

`{ ok: false, error: 'invalid_auth' }` 配 200。只看狀態碼的實作會把「憑證已失效」當成成功而
拿到一個空清單 —— **而那個症狀與「沒有人提及我」完全相同**，使用者會在一件已經壞掉的事上繼續等。

因此回應分**四**類，而每一條分界都是「處置不同」而不是「原因不同」：

| 類別 | 處置 |
|---|---|
| `auth` | 換一份憑證 |
| **`scope`** | **加 scope 並重新安裝** —— 換新 token 一點用也沒有 |
| `transient` | 等下一輪 |
| `malformed` | 不重試（見下） |

**`malformed` 刻意不併進 `transient`**：併了會讓上層無限重試一個永遠不會成功的呼叫。

**而 `scope` 刻意不併進 `auth`，那是 dogfood 踩到的**：`missing_scope` 被報成「你的憑證不再
有效」，而憑證是完全好的 —— 照那句話做會白換一份 token，而問題原封不動。
**Slack 在回應裡就給了 `needed` 與 `provided`**，而第一版的用戶端把它們丟掉了 ——
那是這則訊息**唯一可行動的部分**。

## 四、Electron 主行程的 `fetch` 走 **undici**，不是 Chromium 的網路堆疊

替身 Slack 是真的 HTTPS 伺服器（產品的端點白名單只認 `https:`，而那條不為驗收放寬）。
自簽憑證怎麼被信任，實測結論：

- **`--ignore-certificate-errors` 無效。** 錯誤碼是 `DEPTH_ZERO_SELF_SIGNED_CERT` ——
  那是 **Node 的** TLS 錯誤，所以 Chromium 的旗標碰不到它。
- **`NODE_EXTRA_CA_CERTS` 有效。**

那個錯誤碼本身就是線索：**看到 Node 形狀的錯誤碼，就不要再往 Chromium 的旗標找。**

## 五、單元測試會靜默地打到真實的 Slack

`slack-service.test.ts` 的第一版沒有覆寫端點，於是它用**預設端點**跑了起來：把一個假憑證送到
真實服務、讓測試依賴網路，而且 Slack **正確地**回了 `invalid_auth`，於是
「網路問題不該被報成憑證失效」那條斷言**以一個完全正確的實作失敗了** —— 症狀看起來像產品的 bug。

那不是紀律問題（預設端點是對的，產品就該連真的 Slack），所以有一道守衛：
`scripts/slack-test-isolation.test.mjs`。**新增碰到 `SlackApi` / `SlackRuntime` 的測試時，
一定要注入 `fetchImpl` 或把 `setApiBaseUrl` 指向本機。**

## 六、機密有**四**條出口，而第四條是新的

| 出口 | 守衛 |
|---|---|
| IPC 投影 | 逐欄位白名單，且機密不在偏好那個物件裡；**Slack 連線設定的投影也算一條**（它本來就要送出去，而憑證住在它隔壁） |
| 子行程環境 | `process.env` 的指派**只允許 `user-env.ts`** —— `ptyEnv()` 展開它，所以洩漏不需要經過 `terminal.ts` |
| 診斷輸出 | `Secret` 的 `toString` / `toJSON` / `util.inspect.custom` |
| **網路** | `reveal()` 只能在白名單模組中被呼叫 —— **那份白名單就是「憑證會被送到哪裡」的清查起點** |

### 絕對不要把憑證放進 shell 的 rc 檔

**`ptyEnv()` 把使用者的互動 shell 環境合併進每一個 pty。** 因此把 Slack（或任何服務的）憑證
`export` 在 `~/.zshrc` / `~/.bashrc` 裡，等同讓**每一個 agent session 都讀得到它** ——
包含使用者在別的 repo 裡跑的、由不受信任的內容（那些 repo 裡的任意 markdown、pty 的輸出）
驅動的那些。

這是一條**無條件**的文件要求（`secret-scope` 明文），而不是「若有需要」：使用者自己的 shell
環境不在應用程式的控制範圍內，所以唯一能做的就是把這件事說清楚。**憑證請只透過
Settings → Integrations 設定**（was the inbox's Slack tab until `settings-sections`） —— 那條路會落在 `<userData>/secrets.json`（僅擁有者可讀寫），
而它不進任何子行程的環境。

三件實測的細節：

- **`process.env` 那道守衛的範圍不能限於「被 `terminal.ts` 匯入」**。真正的向量是任何模組往
  `process.env` 寫，而那個模組不必被它匯入。CLAUDE.md 早已列為承重，只是此前沒有守衛。
- **守衛豁免 `user-env.ts`（唯一的套用點），那個缺口由行為測試補**：pty 環境的任何一個值都不含
  機密。兩者**互補而非重複**，已實測配對（在 `user-env.ts` 寫一行洩漏 ⇒ 守衛仍綠、行為測試變紅）。
- **行為測試必須呼叫 `ptyEnv()` 不帶參數**。第一版傳了明確的 `source`，於是繞過了 `process.env`
  這個真正的向量 —— 一個真的往 `process.env` 寫機密的實作，那條照樣綠。

## 七、`Secret` 的隱私來自 private field，`inspect.custom` 提供的是**可讀性**

`#value` 是真正的 private field，`util.inspect` 本來就看不見它（只會吐 `Secret {}`）。所以
「`inspect(secret)` 不含明文」這條斷言對**沒有**覆寫 `inspect.custom` 的實作一樣成立 ——
零鑑別力。

`inspect.custom` 真正提供的是**可讀的 redaction 標記**：讀 log 的人要知道那裡有一份機密被略過，
而不是以為那個欄位沒有值。**斷言要釘標記本身。**（若 `#value` 日後被改成普通欄位，隱私就真的
落在 `inspect.custom` 上了。）

## 八、檔案權限是「持有」而不是「建立時設定」

`fs.writeFileSync` 的 `mode` **只在檔案被建立時生效**。三種情形：

- **目標檔已存在且權限較寬** ⇒ `mode` 完全無效。處置：一律「暫存檔 → rename」。
- **暫存檔已存在且權限較寬**（前一次寫入崩潰留下的）⇒ `mode` 同樣無效，而它的權限接著會被
  `rename` **帶到目標檔上**。處置：寫完暫存檔後明確 `chmod`。
- `load()` 也要收緊 —— 檔案可能在兩次執行之間被外部改寬。

> **那個明確的 `chmod` 不是防 umask**（umask 只會**清掉**位元，`mode: 0o600` 不可能因此變寬）。
> 第一版的註解把理由寫成 umask，而那條理由的對照組不會變紅。

而「目標檔已存在」那條測試的第一版是**假綠**：它在建立寬檔案之前就呼叫了 `load()`，於是
`load()` 的收緊搶先把它變成 0600 —— 它靠那個通過，而「改成直接寫目標檔」的對照組不會變紅。
**寬檔案必須在寫入路徑之前、且在 `load()` 之後才出現。**

## 九、`Record<keyof T, Spec>` 與 homomorphic mapped type 的守衛強度不同

偏好欄位表用的是：

```ts
{ [K in keyof Required<TerminalPreferences>]: FieldSpec<Required<TerminalPreferences>[K]> }
```

**不是 `Record<keyof TerminalPreferences, FieldSpec>`。** 後者讀起來等價，但 `Record` 的鍵型別
受限於 `keyof any` 而非 `keyof T`，於是它不是 homomorphic，`FieldSpec` 拿不到逐欄位的 `T` ——
把 `fontFamily` 接上 `clampSize` **零錯誤**。

實測（repo 自己的 tsc）：漏欄位 `TS1360`、漏答一個問題 `TS2741`、清理器接錯 `TS2322`、
新增字型欄位而未接進 `setTerminalFont` 的參數組 `TS2741`。**照 `Record` 實作會用一個新的靜默
失效換掉舊的** —— 從「三處各自為政」換成「表是單一來源但每一格接錯無人知」。

> **編譯期的保證目前沒有自動化載體。** 上面四條都是人工跑過的對照組，而沒有東西會在那個型別
> 被改回 `Record` 時變紅。已登記為 issue。

## 十、`preload` 寫寬了，主行程的白名單就只剩執行期效果

renderer 的偏好型別是自 preload 回推的（`shell/types.ts` 的 `Awaited<ReturnType<…>>`）。
只窄化主行程時，renderer **仍然寫得出**讀未送出欄位的程式碼，而它永遠是 `undefined` ——
症狀是一個安靜地永遠走 else 分支的判斷。

這條是**對照組抓出來的**：第一版只窄化了主行程，註解裡寫著「renderer 讀未宣告的欄位是編譯
錯誤」，而「在 renderer 讀 `agentEvents`」那個對照組**沒有變紅**。
**沒有那次對照，那句假話會留在註解裡，而下一個人會相信它。**

## 十一、`probe:slack` 的兩個實作陷阱

- **替身必須真的套用 `oldest`。** 不套用的話「回看範圍之外的提及不出現」會因為替身不篩而假綠
  —— 那條斷言會變成在測產品有沒有自己再篩一次，而它不該再篩。
- **數卡片張數，不要數子字串出現次數。** 一則提及的文字同時出現在標題與本文裡（同一張卡片），
  於是「出現兩次」對一個完全正確的實作也成立。

另外：**狀態的斷言要拆成兩層**（先讀 IPC payload、再讀畫面）。分開之後「主行程沒記下」與
「畫面沒更新」是兩條不同的紅燈，而它們的處置完全不同 —— 第一次跑這支 probe 時主行程那一層
就是綠的，直接指著 renderer（那是一個真的缺陷：狀態沒有推送）。

## 十二、回補必須是週期性的，不能只在啟動時跑（dogfood 踩到）

第一版是一次性的 `setTimeout` —— design D1 的降級模式寫的是「啟動時 **+ 週期輪詢**」，
而只做了前半。踩到的方式很普通：**使用者在 app 起來之後才貼上憑證**，那一輪早就跑完了，
而不重開 app 就永遠不會有第二輪。

而在 dev 模式下這件事更糟：**關掉視窗會結束整個 `npm run dev`**，於是「重開 app」需要有人
重跑那個指令。

三個觸發點，各自有理由：

- **啟動後一次**（延遲數秒，不與啟動搶資源）。
- **每 5 分鐘一次** —— 即時路徑是加速器且可能根本不可用，所以這不是備援而是主幹的一部分。
- **使用者存下憑證的那一刻** —— 那正是該去試一次的時機，而少了它他看到的是一個什麼都沒變的
  畫面，與「功能壞了」無法區分。

三者會重疊，所以 `runRound()` **不可重入**（一個 `#running` 旗標）；`setInterval` 要
`unref()`，否則主行程在該關的時候關不掉。

## 十三、對端說「等一下再來」時要真的等 —— 而「解析了」不等於「用了」

`Retry-After` 曾經被**解析得好好的**（`slack-api.ts` 把它放進 `retryAfterSeconds`），而
**全 repo 沒有任何消費點**。於是被限流時的行為是照原節奏繼續敲一個正在說「等一下」的服務。

`grep -rn retryAfterSeconds src/` 只命中型別宣告與那個產生處 —— **一個只有生產者沒有消費者的
欄位，看起來與「已經做了」完全一樣**，而型別檢查對此完全無感（它是 optional 的）。

三件當時沒想到、追下去才發現的事：

- **逐頻道的迴圈在失敗時 `continue`** —— 被限流的不只是「下一輪」，是**這一輪剩下的每個頻道
  都會照樣打，而每一個都會再被拒絕**。30 個頻道在第 5 個被擋，還會再送 25 次註定失敗的請求。
- **速率上限不一定發生在迴圈裡。** `auth.test` 與 `users.conversations` 在迴圈**之前**，
  而它們的早退如果只回傳 `failure`，退避資訊就一併遺失 —— 症狀是「被限流時完全不退避」。
  **加一個橫切的狀態時，把那條路徑上所有的早退都走一遍。**
- **「先到的贏」的欄位會把後到的資訊吃掉。** `failure ??= …` 讓第 2 個頻道的網路錯誤佔住
  `failure`，於是第 5 個頻道的 429 永遠讀不到。**退避資訊因此走 outcome 的獨立欄位**，
  兩者互不遮蔽。考慮過「讓速率上限優先覆寫」——否決：那是在既有優先序上疊一條例外，
  而下一個加失效種類的人不會知道它存在。

### 等待時間要夾上下界，而上界的理由不是「不相信 Slack」

**端點是使用者可設定的**（`slack-settings-store`）。一個回 `Retry-After: 99999999` 的端點會讓
這個能力**無限期停擺**，而畫面上只會顯示「正在等待」。
**一個能被輸入資料無限期關閉的能力，是一個可以被關掉的能力。**

下界同理：缺席或 0 都要當成「一段保守的時間」而不是零 —— 對端已經明確拒絕了，零等於不退避。

### 跳過一輪與漏掉那段期間，是兩件事

被跳過的那一輪**不排隊補做**（補做會在解禁的那一刻形成尖峰，正是限流要避免的事），
而水位機制保證那段期間發生的提及會在之後的取回中出現。**規格上要把這兩件事分開講**，
否則下一個人會以為跳過的那一輪的內容沒了，然後去加一個補做機制。

### 而使用者按下去的那一次不能靜默跳過

存下憑證卻什麼都沒發生，與「功能壞了」在畫面上完全相同 —— 一次靜默的跳過會讓
「失效與閒置必須可區分」那條 requirement 在這條路徑上作廢。退避期內被觸發時**仍然要推一次
狀態**，並說得出下次何時會試。
